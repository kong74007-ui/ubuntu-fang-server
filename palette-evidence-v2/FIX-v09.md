# v09 阻断项的发现与修复

## 1. 阻断现象（已修复）

按方案的原始目标值放大 v09 四层字号（`100 / 62 / 72 / 78 px`）后，**真实 App payload 在生产链路上被直接拒绝**：

```
validate_payload(raw, require_reference_semantic_layout=True)
  -> _reference_semantic_text_layout()
    -> _pack_reference_semantic_span(top, 0, top1_end=12, top_break_after=[11,17], contract["top1"])
       -> ValueError: HyperFrames 文案无法在完整语义边界内排入模板
```

经 `/v1/jobs` 返回给 App 即 **HTTP 400 → 任务创建失败**（不是视觉问题，是功能不可用）。

## 2. 定位过程

用生产 `api.py` 对同一份真实 payload 做**逐层字号扫描**：

| 尝试 | 结果 |
|---|---|
| 方案值 `100 / 62 / 72 / 78` | ❌ 失败 |
| `top1` 扫 88 / 90 / 92 / 96 / 100 | 只有 **88 ✅**，90 起全部 ❌ |
| `top2` 扫 62 / 70 / 78 / 86 / 94 | 全部 ✅（有富余） |
| `bottom1` 扫 72 / 78 / 86 / 94 | 全部 ✅（有富余） |
| `bottom2` 扫 70 / 78 / 86 / 94 | 78 ✅，86 起 ❌ |

**根因（第一性原理）**：该 payload 的 `top1_end = 11` 把 `top1` 的语义跨度锁死为
`选赛道别只看谁现在最火`（11 字），这个跨度内部**没有任何 AI 断点**
（`top_break_after` 只有 11、17 两个位置），因此**只能排一行**；
行宽预算 `max_width_px = 996`，而 88px 已经贴着这个上限——**任何放大都会溢出**。

这不是排版 bug，而是"AI 给出的语义跨度只能单行"与"字号上限"共同决定的硬约束。

## 3. 修复方式（按方案自带的兜底顺序）

方案原文对"溢出"给出的处理顺序是：

> 1. 允许辅助文案换行；2. 适当收紧字间距；3. 最后才小幅降字号，**最低不得低于当前字号**。

而 v09 的 `top1` 无处可换行、字间距也补不回 100+px 的差距，因此按第 3 条落到**当前字号**：

| 层 | 改前（生产） | 方案目标 | **本 PR 落地** | 说明 |
|---|---|---|---|---|
| `top1` | 88px | 100px | **88px（不变）** | 已贴宽度上限，兜底到"不低于当前字号" |
| `top2` | 50px | 62px | **62px** | ✅ 放大 |
| `bottom1` | 60px | 72px | **72px** | ✅ 放大 |
| `bottom2` | 66px | 78px | **78px** | ✅ 放大 |

这也正好对应用户的原话——"字号偏小，**特别是辅助文案和底部文案**"，
被放大的正是辅助层与底部层；`top1` 本来就是 88px（比它们都大），不放大不影响层级。

其余限制全部遵守：字体（`MaShan`）、字重、描边宽度、行高比例、位置、安全区均未改动。

## 5. 遗留提示（供后续决策）

`top1` 想真正放大到 100px，只能由**调用方**在 `semantic_layout` 的第一分句内也给出断点
（例如 `选赛道｜别只看谁现在最火`），这样服务端即可把 `top1` 排成两行。
这属于 App 侧 AI 的行为，不在本仓库范围；本 PR 不改断句与排版。
